实验一：把推理判成有效

本节目标：用标准库写出真值表引擎，把课件 1.8 的整批推理一次判定，并对上你纸上写的那几份证明。

这一节不引入新知识

前面两课已经把两样东西交给你了：第 1 课给了一套编号（小项 m_i、大项 M_i，以及 \Sigma m 与 \Pi M 的写法），第 2 课给了一套证明（前提逐条写 P、结论拆成蕴含、三条路线各自的首行与末行）。

这一节把这两样接起来，做成一个能跑的东西：给它一组前提和一个结论，它穷举全部赋值，判出这个推理有效还是无效，并指出依据——有效时说"全部 2^n 个赋值里没有一个反例"，无效时给出那个反例赋值。

手算只判过一题，课件 1.8 上却有几十道。这件事本来就该交给程序。

要做出什么

三样，都是可观察的产物：

  1. engine.py 里 7 个留白函数填完，python -m unittest -v test_engine 21 条全绿；
  2. python report.py 打出 16 行，每行是「编号｜判定｜依据｜出处」——判无效的那 5 道带出反例赋值，判有效的 11 道写「反例 0 / 2^n」；
  3. audit.py 里的 MY_ANSWERS 填满 16 道，python audit.py 打出两轮对账、对不上 0 道：第一轮引擎与课件答案，第二轮引擎与你纸上写的。

第 3 样才是这次实验的正题。前两样是手段。

怎么算过

照被验收的两课的 objective 逐条落地，四条都过才算过。

一、编号要对得上第 1 课。 第 1 课的要求是「把公式化成主析取范式，并读出它的成真赋值」。这里把它反过来用：给它一个公式，程序要能算出 \Sigma m 的那组编号，并说出每个编号对应的赋值是什么。判据是 TestMinterms 那三条——$P\to Q$ 的 \Sigma m 是 [0,1,3]（只有 10 那一行是假），三个变元时 P\wedge Q 是 [6,7]，重言式占满全部编号、矛盾式是空表，\Sigma m 与 \Pi M 合起来正好占满 0\ldots 2^n-1。编号规则与纸上那张表逐字一致：变元按字母顺序排，第一个变元占最高位，真记 1。

二、判定要落在「前提合取蕴含结论是重言式」这一句上。 这是第 1 课末尾埋的那句话，也是第 2 课定义 1.8.1 的原话。落到程序里就一行：反例 = 前提全真且结论为假的赋值；反例一个都没有，推理有效。判据是题库 16 道的判定与课件答案逐道相等（TestBank），而且判「无效」的每一道都拿得出反例——这正是 report.py 中间那一栏。

三、要与纸上那 8 道证明对账。 第 2 课验收的是「用 P、T 规则写出三步以上的推理证明，格式不空转」。这一课验同一批题的另一面：你纸上写得出证明的题，引擎必须判有效；引擎判无效的那几道，你纸上一定写不出证明——因为证明的每一行要么引前提、要么按规则从已有的行推出，而"前提真、结论假"的那个赋值会让其中的某一步当场断掉。对不上的那一题，你要能指出它断在第几行（通常是偷偷把结论当成前提写成了 P 行）。

四、交付物要自证。 两轮对账都打出 0 道，且 report.py 的每一行都有依据。这不是"我觉得对了"，是程序把 16 道逐题算了一遍、再与两份答案表逐题比了一遍。

四句话说完：要做出什么是一台能判有效性的真值表引擎；怎么算过是它的编号对上第 1 课、判定对上课件、结论对上你纸上那 8 道证明，两轮对账 0 道差异。

从哪一步开始

任务书在 lab · 真值表引擎，六步：穷举赋值 → 递归求值 → \Sigma m 编号 → 反例与有效性 → 对账 → 看报告。每步都是"一小段讲解 + 立刻能跑的断言"，跑完那一步的类再往下走。索引与文件分工在 lab 总目录。

数据格式与前两节完全相同（'P'、('imp','P','Q') 这套嵌套元组），题库、报告、对账三份文件都已写好，你只填 engine.py 的 7 个函数和 audit.py 里的 MY_ANSWERS。

上手做 交 lab：把引擎跑绿

先进目录、跑一次，看清红在哪：

cd lab/0003-truth-engine
python -m unittest -v test_engine

这时全是 NotImplementedError: 任务 1：……。按任务书的第 1 步往下填，填一段跑一段：

python -m unittest -v test_engine.TestValuations
python -m unittest -v test_engine.TestEvaluate
python -m unittest -v test_engine.TestMinterms
python -m unittest -v test_engine.TestValidity

四类都绿了再填对账那一步，然后看两份输出：

python report.py
python audit.py

保底提示：MY_ANSWERS 先在纸上判，再填。倒过来做（拿 report.py 的输出抄进去），这一课就只剩格式，看不出你哪一题判反了——而对账的全部意义就在那几道对不上的题上。

自查清单

  • python -m unittest -v test_engine 21 条全绿；python report.py 16 行；python audit.py 两轮 0 道。
  • 判无效的 5 道（C11、C12、C13、C15、C16）报告里都带反例赋值，且你逐一代回前提验过一次。
  • 不看代码能说出：反例为什么必须同时满足「前提全真」与「结论为假」；漏掉前者会让哪几道判反。
  • 不看代码能说出：「无效」不等于「结论为假」——举 C11 的一个赋值说明。
  • 不看代码能说出：n 个变元有几个赋值、编号怎么排、\Sigma m 与 \Pi M 为什么互补。
  • 能说出 C14（前提是 P 与 \neg P）为什么判有效，以及它与你纸上写归谬法时"推出矛盾"那一步是同一件事。
  • 那 8 道纸上写过的题：引擎判定与你的证明对得上；对不上的那一题，你已指出它断在第几行。

最可能卡在哪

一、编号的位序写反。 这是第 1 课就埋下的坑，这次由断言逐题报出来。表现有两种：TestValuations 报「第 5 项应当是 101」，或者 TestMinterms 报 Σm 编号不对。麻烦在于位序反了之后，编号看起来照样像编号——P∧Q 会算出 [3, 7] 而不是 [6, 7]，只差一次镜像而对不上任何手算结果。自查一句：三个变元时 P 乘 4、Q 乘 2、R 乘 1，P=1,Q=0,R=1 是 5。

二、反例只判了一半。 只写 evaluate(conclusion, env) == 0（漏"前提全真"），会把"前提本来就不成立"的赋值也算成反例，于是 16 道全判无效；只写前提全真，则结论为真的行也被算进去。TestBank 会一次报四五道，报错信息里那几道基本都集中在 C14（前提自相矛盾）周围——它反例为零，最容易被误判。修法就一句：两个条件用 and 连起来。

三、把「无效」读成「结论为假」。 无效只说明存在一个赋值让结论落空，结论在别的赋值上照样可以为真。这一条不会让测试变红，却会让对账表失去意义：C11 的反例是 01，依据是"P\to Q 与 Q 在这个赋值上全真，而 P=0"，而不是"P 算错了"。报告里那一栏写的就是这件事——中间那一格是反例赋值，不是结论的真值表。

这一块地基后面一直要用

这套东西不是实验一用完就算：贯穿项目是「关系与图算法工具包」，同一套编号与断言风格要在后面四个实验里反复出现——实验二的关系矩阵按同样的位序编号、同样的对账表与教材逐格比；实验三的等价类与拓扑序复用这里的断言三段式；实验四、五的手算表同样要能一列一列对上程序输出。把编号写对、把反例判准、把对账做成一张能一眼看出差异的表，这四件事在这一节练熟，后面四个实验每个都省一半力气。
